# Batch 5B — isolated SLO performance benchmark

This is a synthetic, local benchmark of the existing exact research calculations, not a production capacity certificate or approval to deploy. No production database, credentials, checks, baseline, proposal, or threshold were used or changed. No SLO/SPC formula, index, migration, or application workflow was changed in this batch.

## Environment and reproducibility

- Host: Intel Core i5-10310U (4 cores/8 logical CPUs), 15 GiB RAM; approximately 2.4–3.0 GiB available during the runs, with the 2 GiB host swap already nearly full. Approximately 11–12 GiB filesystem space was available. This constrained setting is not representative of production.
- Disposable `mysql:8.4` container: MySQL **8.4.8**, 2-CPU and 768-MiB limits, no persistent volume; observed memory about 522–645 MiB. The disposable schema occupied about 90 MiB on disk at 500,000 checks. InnoDB buffer pool 128 MiB; `tmp_table_size` and `max_heap_table_size` 16 MiB each; sort buffer 256 KiB; `REPEATABLE-READ`, strict SQL mode.
- PHP CLI **8.4.27**, Laravel **12.62.0**. Benchmark process memory limit 256 MiB. The measured one-worker process peaked at 54.5 MiB; a separate 500,000-row analysis process peaked at 50.5 MiB. These are PHP allocator figures, not total host memory.
- Isolated queue and cache drivers: Laravel `database`; one `queue:work` worker, `--stop-when-empty --sleep=0 --tries=3 --timeout=60 --max-time=120`, at most 50 jobs. The ordinary Compose worker instead uses `--sleep=3 --tries=3 --timeout=60 --max-time=3600`; idle pickup latency under that configuration was **not measured**.
- The fixture is generated by [`tests/Benchmarks/slo_performance.php`](../tests/Benchmarks/slo_performance.php). **It deletes fixture records.** Use a newly created, no-volume local MySQL 8.4 container, never a development or production server or credentials. Before running migrations or the benchmark, create the dedicated `svu_b5b_only` user with grants limited to `svu_b5b_disposable`; manually create `svu_benchmark_guard (id INT PRIMARY KEY, token CHAR(48) NOT NULL)` in that schema and insert `(1, <fresh random 48-character lowercase hex token>)`. Record that container's `SELECT @@server_uuid`. The runner requires `SVU_BENCHMARK_ALLOW=yes`, `SVU_BENCHMARK_GUARD_TOKEN` matching the database marker, `SVU_BENCHMARK_SERVER_UUID` matching the server, the dedicated user, MySQL 8.4, and the exact local host `127.0.0.1`, port `33071`, database `svu_b5b_disposable`; it fails closed if any check fails. These independent checks guard against a misleading environment name or a localhost tunnel pointing at another server. Do not reuse the marker or credentials. After migrations **in that isolated schema only**, run `php tests/Benchmarks/slo_performance.php seed 40000`, then `measure`, `queue 1`, and `probe`, with the guarded environment variables set. Repeat `seed 100000`, `seed 250000`, `seed 500000` for the other sizes. The runner limits PHP to 256 MiB and refuses or stops seeding below 8 GiB free disk or 1.5 GiB host available RAM; the Docker container provided the 768-MiB/2-CPU database ceiling. A wrong-marker test refused execution before fixture deletion. The container was stopped and removed after verification.

The fixed arithmetic seed is **20261116** (no runtime RNG). All checks lie in the 28 complete Asia/Damascus days stored as UTC `[2026-10-18 21:00:00, 2026-11-15 21:00:00)`. Every size has exactly 50 heterogeneous inactive HTTP/API bulk services plus 61 separately grouped active-on-demand daily-cadence queue services and one lifecycle fixture. Bulk service counts are unevenly weighted; latency uses service-specific base values, deterministic moderate variation, and a roughly 5% slow tail. The 500,000-row fixture contained 337,120 HTTP and 162,880 API checks; 9,969 manual-source checks, 4,988 maintenance-flagged checks, 17,426 failures, 4,997 missing latency values, and 24,046 slow classifications (categories can overlap). Check timing and configured cadences produce variable coverage and missing opportunities. Negative latency cannot be inserted into the existing MySQL unsigned column; invalid-latency semantics remain covered by regression tests, not this bulk fixture. No university data were copied.

## Method

For each dataset size, `measure` selected the smallest, median-sized, and largest bulk service. Five sequential calls each to `LatencyPercentileAnalysis`, `SliIndicatorAnalysis`, and `SloCalibrationAnalysis` used the same historical snapshot and fixed clock. The table below gives the median and R Type 7 p95 **of five benchmark runtimes**; that runtime p95 is descriptive only and must not be confused with the monitoring-latency P95. The first call is a process-level cold-ish run; later calls are warm-ish. MySQL buffer/cache state was not forcibly cleared, so this is **not** a controlled cold-cache comparison. Laravel's query listener counted SQL calls and summed driver-reported SQL time. Results were checked for deterministic repeatability. Preparation was measured once for a separate eligible daily-cadence service and then repeated; authorized review/approval and five independent post-approval evaluations used only synthetic data. Queue cohorts of 1, 10, and 50 were dispatched through `slo:prepare-due`, re-dispatched on the same simulated local day, and drained by one bounded worker.

## MySQL plans and database activity

Existing `service_checks` indexes include the primary key, `(monitored_service_id, checked_at)`, `(monitored_service_id, is_during_maintenance, checked_at)`, and the maintenance-window FK index. `EXPLAIN FORMAT=TREE` selected one of the service/time indexes depending on data size and estimates. At 500,000 rows, `EXPLAIN ANALYZE` for the exact largest-service percentile query showed an **index range scan of 18,219 service rows** (about 50 ms), eligibility filtering to **16,856** rows, then a response-time sort, windowed `ROW_NUMBER`, materialization, and a scan of that **derived ranked subset** to select eight ranks. Total measured SQL-plan time was about **81 ms**. The derived-table scan is not a full scan of the 500,000-row base table. A same-cohort ranking probe created one session temporary table, zero disk temporary tables, and one sort merge pass; it did not prove that larger cohorts will avoid disk spills. No new index is justified by this result: the dominant application-level elapsed time at high per-service density includes streamed coverage enumeration and model hydration, while the exact rank requires sorting the eligible subset. Further optimization needs profiling and equivalence tests, not a speculative migration.

## Scheduler, queue, retries, and contention

| Cohort | First scheduler dispatch | Repeat same-day dispatch | One-worker drain | Median / max job | Result |
| ---: | ---: | ---: | ---: | ---: | --- |
| 1, at 40k | 0.108 s / 1 job | 0.006 s / 0 jobs | 0.132 s | 91 / 91 ms | 1 proposal, 0 failed |
| 10, at 100k | 0.543 s / 10 jobs | 0.031 s / 0 jobs | 0.903 s | 77 / 90 ms | 10 proposals, 0 failed |
| 50, at 250k | 2.501 s / 50 jobs | 0.133 s / 0 jobs | 4.307 s | 70 / 101 ms | 50 proposals, 0 failed |
| 50, at 500k | 2.369 s / 50 jobs | 0.139 s / 0 jobs | 4.277 s | 72 / 83 ms | 50 proposals, 0 failed |

At 500,000 rows, the 50-job run processed all jobs with zero backlog and a 54.5-MiB worker PHP peak. Since fixture time is frozen, database queue timestamps cannot be compared directly with the real monotonic clock. For that clean batch, median enqueue-to-start wait was **bounded between 2.17 and 4.68 seconds**; maximum wait was between **4.21 and 6.72 seconds**. This includes scheduler dispatch and the explicit same-day recheck. Two simultaneously executed scheduler scans of a fresh 10-service cohort dispatched **4 + 6 = 10** jobs, which produced exactly 10 proposals after one worker drained them; no duplicate, error or retained job was observed. This is one concurrency trial, not a proof for all races. The existing focused tests cover dispatch failure cleanup, retry/terminal failure, gate preservation, transaction rollback, and lifecycle integrity. Failure injection and worker crash recovery were **not load-benchmarked** here.

The original queue run counted successful worker completions and final proposals but did not independently count which jobs executed the expensive percentile query. A **separate bounded repeat** on a freshly seeded 500,000-check disposable schema instrumented the worker's exact `ROW_NUMBER()` percentile statement: **50 dispatched, 50 completed, 50 full ranked calibrations, 50 new Draft proposals, 0 jobs without ranked calibration, 0 existing-proposal exits, 0 insufficient-evidence exits, 0 failed jobs, and 0 remaining jobs**. Before dispatch this cohort had zero proposals; all 50 services had 28 eligible daily checks, so these exit categories are exhaustive for this controlled run. The same-day second scheduler invocation dispatched zero. Repeat timings were **2.434 s for dispatch**, **4.212 s to drain one worker**, with **70.756 ms median job execution** and **52.5 MiB worker PHP peak**. These measurements are separate: dispatch throughput is 50/2.434 ≈ **20.5 jobs/s**, queue completion is 50/4.212 ≈ **11.9 jobs/s**, and actual full-calibration throughput in this light 28-check-per-service cohort is also **11.9 calibrations/s**. The previously reported 2.369 s / 4.277 s timings remain valid for their run, but by themselves did not establish the number of full calibrations. None of these rates predicts throughput for 50 dense services with thousands of checks each.

The 00:35 institution-local SLO schedule follows daily reliability at 00:10, SLA at 00:20, and legacy control charts at 00:25. `spc:evaluate` and `services:check-due` also run every minute. Phase I automatic baseline preparation is available through a separate workflow, not a nightly scheduled command. `withoutOverlapping()` protects each scheduled event from itself, not from other commands. SLO, monitoring checks, and Phase I preparation use the same default database queue and worker in the inspected Compose configuration; simultaneous heavy calibration may therefore delay monitoring even though SLO work is queued. A 400-query indexed synthetic read probe on the 500,000-row fixture had median / p95 **0.845 / 3.173 ms** without SLO jobs and **1.069 / 3.470 ms** while 50 SLO jobs ran. These single short probes suggest modest database-read contention in this fixture only. Due HTTP check dispatch latency, request completion delay, control-chart overlap, and a project-defined acceptable delay threshold were **not measured**, so no claim of non-interference is made. Parallel workers were not tried because host swap was full and the MySQL container already used about 645/768 MiB.

## Scientific verification, limits, and decision

No application optimization was made; there is no before/after code comparison. The 28 complete local-day UTC cutoff, maintenance/manual exclusions, exact R Type 7 ranks, `S/N`, `G/V`, `G/N`, P90/P99 rounding, strict frozen digest, permissions, lifecycle, SLO/SPC independence, and immutable historical measurements remain as established. Final focused scientific/scheduler/lifecycle regression on a **second disposable MySQL 8.4.8 schema** passed **122 tests / 888 assertions**. The full SQLite application suite passed **620 tests / 3,836 assertions**. Pint, PHP syntax validation for the benchmark runner, `git diff --check`, and a guard-refusal check without the required disposable connection passed. The benchmark container and both synthetic schemas were removed; no production service was contacted.

Recommended **benchmark-derived provisional operating envelope**, not a production guarantee: at most the tested 50 new SLO candidates in one daily dispatch until heavier service mixes and the shared queue are retested; retain one worker for initial isolated testing, the existing 55-second SLO-job and 60-second worker timeouts, and a monitored queue-depth/oldest-job-age alarm before rollout. The current scheduler does **not** enforce a 50-job cap; if the eligible population can exceed it, an explicit fairness-preserving dispatch policy or queue isolation needs separate review. Do not infer that 50 dense services would finish in 4.3 seconds—the measured queue cohort had only 28 calibration checks per service. Define an acceptable monitoring-delay limit and test real check-dispatch latency under concurrent SLO, SPC, and nightly reliability workloads before production activation. Do not change indexes or exact statistics based on this fixture alone.

**Go for Batch 5C planning, no-go for deployment/Pilot on this evidence alone.** Remaining gaps include real service-size and arrival distributions, genuine cold-cache behavior, long-lived worker memory, two-worker behavior, lock-wait instrumentation, queue crash/retry load, schema-statistics drift, historical configuration changes, and end-to-end monitoring delay. Synthetic response-time values are not browser experience or externally validated SLO targets.
