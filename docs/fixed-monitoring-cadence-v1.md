# Fixed monitoring cadence v1 — implementation for review, not deployment authority

Policy `fixed-utc-slot-v1` replaces the prior `latest service_checks.checked_at + interval` scheduling rule **only after** an explicitly configured UTC-minute cutover. The feature is disabled by default. No production migration, configuration change, or activation is part of this work.

## Nominal schedule and opportunity states

For an interval of *m* minutes, nominal UTC slots are exact UTC timestamps whose Unix-minute number is divisible by *m*. An epoch starts at the first such slot at or after the explicit cutover, service creation/reactivation, or a monitoring-configuration change. The epoch stores the policy version, interval, safe configuration snapshot/fingerprint, UTC effective bounds, and next unprocessed nominal slot. Service-row locking serializes scheduler polls; a unique service/nominal-slot key and one active epoch key provide database-enforced duplicate protection. A service has at most one queued/running opportunity; later due slots become `missed` with `previous_check_pending`, never extra overlapping checks. Slots missed because a poll was absent become `missed` with `scheduler_poll_missed`. Missed slots have **no** synthetic `service_checks` row. The scheduler accounts at most 120 slots per service per poll, continuing older backlog on later polls; while catch-up remains, completeness is explicitly unknown.

`queued`, `running`, `completed`, `missed`, `failed`, and `cancelled` are separate ledger states. `dispatched_at_utc` is recorded when the database queue insert succeeds, `started_at_utc` when a worker claims the opportunity, and `completed_at_utc` with persisted result or terminal noncompletion. `service_check_id` links a completed opportunity to one real check. The `checked_at` field remains the checker start, **not** nominal due or HTTP completion. Automatic checks continue during maintenance and retain the existing `is_during_maintenance` exclusion from research. Manual checks never move the nominal cursor. Disabled services close their active epoch; reactivation opens a new one without claiming the disabled period was monitored.

Dispatch, ledger insertion, and cursor advancement share one database transaction. This requires the monitoring queue's database driver, queue connection equal to the application database, `after_commit=false`, and `retry_after` greater than the job timeout; an unsupported queue configuration fails closed before dispatch. Dispatch failure rolls back the slot and queue write. Workers claim by row lock and a per-attempt token; result persistence locks that row and commits the check and completed status together. A replay cannot create a second persisted check. The existing per-service `WithoutOverlapping` middleware limits concurrent execution; the durable ledger, token and unique indexes are the correctness backstop beyond its 90-second expiry and the older 120-second `ShouldBeUnique` cache lease. A crashed worker's database-queue retry may reclaim after the 90-second execution lease; an error before persistence returns the same opportunity to `queued`, and final queue failure is observable as `failed`. An external HTTP request can nevertheless execute more than once if a worker crashes after sending it but before durable persistence; this design does **not** claim exactly-once external execution. In-flight HTTP calls during a configuration change may finish, but a closed epoch cannot persist an old-policy result afterward.

This design retains database queue jobs; it does not create a new worker architecture. The queue's `retry_after=90` and job timeout of 30 seconds currently satisfy the ordering, but production configuration and worker restarts must be checked. If the flag is turned off after epochs exist, scheduled dispatch stops with an explicit error rather than silently resuming the legacy algorithm. Previously queued fixed-policy jobs cancel before measuring. A deliberate rollback requires an operational/research cutover decision; merely toggling the flag is **not** a complete rollback plan.

## Research comparability and coverage

All previously stored `service_checks`, frozen Phase I baselines, approved SLOs, and Phase II signals remain untouched. A fixed-cadence epoch is a new sampling regime even if the configured interval is unchanged. New automatic Phase I preparation refuses a mixed or already obsolete window. New SLO calibration reports `monitoring_sampling_regime_crosses_calibration_window` or `monitoring_sampling_regime_obsolete_at_preparation` as insufficient evidence; automatic proposal preparation skips it. Existing pre-cutover Phase I and SLO references are marked incompatible for new evaluation after cutover rather than silently combined with the new sample. New separately reviewed references require wholly post-cutover calibration data. These are compatibility guards, not statistical-formula changes. Historical reliability and SPC reports retain their original interpretation and must be labeled pre-cutover.

The existing `MonitoringCoverageCalculator` estimates expected checks from the current interval and observed check timestamps. It is a **legacy estimate**, not a count of recorded nominal opportunities. `FixedMonitoringCadence::opportunityCoverage()` reports the new ledger's due/completed/missed/failed/cancelled/pending counts over a UTC half-open interval and returns no completion percentage while unprocessed backlog exists or the requested interval crosses a regime boundary. Its completed/due percentage is **not** executed-check availability, an SLO, or maintenance-adjusted research coverage. Researchers must keep these measures distinct; no existing SLI/SLO, P-chart, I/MR, or Phase II formula was changed.

## Activation and acceptance prerequisites

Two additive migrations are required, in order: `2026_11_17_000001_create_monitoring_schedule_epochs.php`, then `2026_11_17_000002_create_monitoring_opportunities.php`. They create new tables and indexes only, preserve all existing monitoring records, and refuse rollback when ledger data exists. The opportunity table's `service_check_id` FK is nullable and unique. Approximate storage grows one opportunity per due slot: a one-minute service produces 1,440 rows/day, ~40,320 rows/28 days, plus indexes; real MySQL bytes and index/backup costs need an isolated production-scale estimate. No retention deletion is introduced.

For a future authorized activation, complete database backup/restore validation and migration review, set `MONITORING_FIXED_CADENCE_ENABLED=true` and `MONITORING_FIXED_CADENCE_CUTOVER_UTC=YYYY-MM-DDTHH:MM:00Z` to an agreed future UTC minute, refresh Laravel's config cache, restart scheduler/workers, and verify active config/queue/database topology before the cutover. Drain or explicitly account for pending legacy monitoring jobs before that boundary; their old cache lock is not a durable nominal-slot identity, and otherwise a legacy result can straddle the cutover. Document the corresponding institution-local date/time, policy version, and service configuration history. For existing services, the first fixed-cadence poll must occur within one minute after the cutover; otherwise it fails closed and requires a newly reviewed future cutover. This prevents retroactively labeling unobserved slots as missed. The default-off setting keeps the legacy scheduler until explicit activation.

The safe emergency stop is to set `MONITORING_FIXED_CADENCE_ENABLED=false`, refresh the configuration cache, and restart scheduler and monitoring workers. Pending fixed-cadence jobs then cancel before measurement, and the scheduler fails closed instead of silently running the legacy algorithm. Do not delete epochs, opportunities, or their queue evidence. Recovery requires an explicit operational/research review, restoring the flag with the original recorded cutover and compatible queue topology, refreshing configuration, restarting scheduler/workers, and allowing the bounded ledger cursor to record the outage slots; do not choose a new cutover or erase the old epoch merely to hide the interruption.

Candidate prospective acceptance requirements, **not yet proven production limits**, are one nominal opportunity per configured interval, p95 nominal-due-to-successful-enqueue <=5 seconds, and p99 nominal-due-to-persisted-result <=50 seconds, with zero unexplained duplicate checks and all due opportunities accounted for. These 5/50 values require operational sign-off against actual scheduler poll phase, queue capacity, HTTP timeouts and production service mix; they have not been relaxed to the earlier synthetic 65/105-second bounds. Measure separately nominal interval, dispatch lateness, queue wait, HTTP execution, persistence time, and misses. The deterministic tests prove slot arithmetic and transactional behavior with fake HTTP, **not** a representative 5/50-second latency distribution. A minute-polling scheduler that runs several seconds after the minute boundary cannot meet a 5-second dispatch limit by construction; this must be measured before approval.

Still required before code deployment or activation: production-scale MySQL migration/index/retention review, real multi-process concurrent-scheduler and worker crash/restart trials (the automated tests cover replay and deterministic sequential polls), sustained workload and nightly-overlap trials, queue-delay and deadline distribution measurement, backup/restore drill, monitoring-worker capacity, legacy-job drain, and a reviewed rollback/cutover plan. This work does not authorize deployment, automatic SLO preparation, production baseline creation, or Pilot activation.
