# Batch 4B.1: automatic SLO research proposal preparation

`slo:prepare-due` is scheduled once per institution-local day at 00:35, after the existing daily analytical jobs. The existing Docker scheduler (`schedule:work`) and database queue worker run it; no new scheduler, queue, primary navigation item or researcher-controlled parameters are introduced. The command iterates active HTTP/API services without **any** prior SLO proposal and performs only a bounded minimum-valid-sample query on the latest 28 complete local calendar days. It dispatches one unique queue job per candidate. A page visit does not dispatch or calculate a proposal.

The queued job has three attempts, a 55-second job timeout (below the current 60-second Docker worker timeout and 90-second database retry-after), and a two-hour unique lock per service. It verifies that its policy version, institution timezone and exclusive UTC cutoff still match the current complete-day window. It then locks the service row, rechecks activity, type, absence of **all** prior Draft/Reviewed/Approved/Retired decisions and the minimum sample count, and calculates coverage. Only if the policy's 95% coverage and minimum valid-observation conditions are met does it invoke the existing `SloCalibrationAnalysis` once. The resulting payload must be `provisional_research_only` to be persisted. This preserves the frozen 28-day calibration, eligible automatic checks, maintenance exclusions, no-lookahead cutoff, R Type 7 percentiles, S/N, G/V and G/N, 100-ms upward rounding, 99% *provisional research* combined target and all scientific warnings. It never adapts the target to make historical compliance pass.

An atomic per-service/per-cutoff cache gate prevents repeated dispatch or coverage work for the same local day, including after insufficient coverage; a dispatch failure releases only a gate acquired by that dispatch. A failed eligibility query for one service is logged and does not starve later services or clear an earlier in-flight gate. The service row lock serializes competing workers. The immutable identity digest is database-unique. The automatic path refuses to create a proposal if the service has any prior proposal, even a retired or insufficient-evidence proposal; it does not silently supersede a research decision or recalibrate daily after a completed proposal. Insufficient observations or coverage leave the service in a waiting state and create no research record. The next daily check may reconsider the rolling window; it does not run percentile calibration while coverage is inadequate. A delayed job with a stale calendar cutoff, changed timezone/policy, or changed configuration fingerprint since dispatch is discarded, not recalibrated on a different context. Configuration changes after creation do not alter the frozen fingerprint; approval/evaluation retain their existing incompatibility safeguards. Historical configuration and maintenance changes within the 28-day window remain a documented validity limitation.

The existing page shows waiting, queued/preparing, or frozen Draft ready for review only to authorized proposal researchers. The transient preparing marker has a two-hour TTL and is removed when the job completes or terminally fails; a worker crash can leave it visible until TTL expiry. Page loading remains read-only and on demand for one selected service. Reliability viewers without `slo.proposals.manage` cannot see Draft details or the preparation marker. The lifecycle remains Review → Approve → Retire through the existing guarded service, with no automatic approval or operational threshold activation.

System-created Drafts have `created_by = NULL` and an audit event with `initiator = scheduled_system`, avoiding false attribution to a human researcher. The original `2026_11_16_000001_create_slo_proposals` migration must precede the additive `2026_11_16_000002_allow_system_created_slo_proposals` migration, which changes only this column's nullability; no historical proposal or monitoring row is rewritten. Its rollback refuses to make the column non-null while system-created rows exist. For a separately reviewed production rollout: first apply both migrations; verify the pre-existing `slo.proposals.manage`, `reliability.view`, and `control_charts.view` permissions are granted to intended roles; then enable the existing institution-timezone scheduler and database queue worker with a shared atomic cache. The scheduler must not run the new command against an unmigrated schema. Failed jobs should be monitored through Laravel's `failed_jobs` and logs, investigated, then retried through the standard queue tooling; job retries do not depend on the daily dispatch gate. This batch does not run migrations, seeders, real proposal creation or deployment.

The 20-observation and 95%-coverage gates are versioned project research-policy choices, not Google or ISO requirements. A 20-point P99 remains exploratory and tail uncertainty is not quantified. Current-cadence coverage cannot reconstruct historical configuration or maintenance changes. Queue latency, per-service 28-day coverage scans, and the 55-second timeout require measurement with the actual service count and data volume before production enablement. A failed job is logged and retried; no half-created proposal survives a failed transaction. There is no automatic replacement after retirement or after an explicit insufficient-evidence proposal—such cases require a separately reviewed research policy.
