# Batch 5C.1–5C.3 — pre-deployment readiness (not deployment authorization)

This document describes the reviewed code and a **future, operator-controlled** rollout. This batch did not access production, deploy, run production migrations/seeders, approve SLOs, modify monitoring thresholds, or start the Pilot. Scientific SLI/SLO/SPC formulas and historical measurements are unchanged. A successful synthetic benchmark is not evidence that monitoring is unaffected in production.

## Execution architecture and time

`compose.yaml` has one application, web, MySQL 8.4, ordinary `queue`, and `scheduler` container. The scheduler runs `schedule:work`; `services:check-due` and `spc:evaluate` are every minute. The institution timezone is read from `InstitutionTimezone` when Laravel resolves the schedule. Daily local times are reliability **00:10**, SLA **00:20**, legacy control charts **00:25**, and automatic SLO eligibility **00:35**. Backup creation/cleanup are **02:00/03:00** local. `withoutOverlapping()` prevents each event from overlapping *itself*, not different events. At deployment verify the actual Institution Settings timezone (expected `Asia/Damascus`), `schedule:list`, the UTC conversion, and the deployed clock; do not infer local times from the server's UTC timezone.

`services:check-due` dispatches `CheckMonitoredServiceJob` to the default database queue; check network I/O may use up to 20 seconds, and the job timeout is 30 seconds. Phase II `EvaluateSpcPhaseTwo`, researcher-triggered Phase I `PrepareAutomaticPhaseOneBaseline`, and notification delivery also use `default`. The daily reliability, SLA, and legacy chart calculations run in the scheduler process, not the queue. The Phase I automatic preparation workflow is researcher-triggered, not a nightly schedule. These workloads still share MySQL, CPU, and (depending on deployment `CACHE_STORE`) a cache backend. Confirm that app, scheduler and both workers resolve the **same cache store and prefix**: unique-job locks, SLO attempt gates and status keys require sharing. The example Docker environment uses a shared file-cache volume; database cache is also supported. Do not use per-container private file caches.

Previously SLO calibration also used the ordinary queue. Batch 5C.1 routes only `PrepareAutomaticSloProposal` to `slo-calibration`. The ordinary worker retains its established configured `DB_QUEUE` path (`default` when unset); an optional Compose profile `slo-preparation` provides **one** capped worker (`--queue=slo-calibration`, 1 CPU, 384 MiB container memory, PHP memory limit 256 MiB, `--tries=3 --timeout=60`). **Do not set `DB_QUEUE=slo-calibration`**: that would collapse the isolation. Its job timeout remains 55 seconds and the database queue `retry_after` remains 90 seconds. A stopped SLO worker leaves SLO jobs pending but does not block ordinary check jobs. It is **not** a separate database, CPU host, or guarantee against MySQL contention. Do not scale SLO workers until measured. The ordinary queue heartbeat now advances only on the configured monitoring queue's activity; a running SLO-only worker cannot mask an absent monitoring worker. The existing System Operations page separately shows the SLO-only worker heartbeat, dedicated queue depth and age of the oldest pending job; an enabled feature with no SLO heartbeat is **down**, not healthy. A disabled feature is labeled **disabled** even if old pending jobs remain visible. These are read-only, indexed queue observations, not proof of future worker capacity. Failed-job count remains shared and must be investigated by queue name/payload. The SLO profile is not started by ordinary `docker compose up` without the profile.

## Activation gate and configuration cache

`SLO_AUTO_PREPARATION_ENABLED=false` is the absent/default value in `config/monitoring.php` and both example environments. The scheduler's 00:35 event has a configuration filter; direct `slo:prepare-due` execution returns zero work while disabled; a previously queued job and the automatic preparation service refuse proposal creation while disabled. Existing human review, approval, retirement and read-only evaluation remain available. No automatic approval or operational `warning_response_ms`/`critical_response_ms` update exists.

Laravel config cache is respected because runtime code reads `config()`, not `env()`. **Changing the `.env` file alone does not change a cached or long-lived worker's effective flag.** For a future disable: stop the optional SLO worker with `docker compose --profile slo-preparation stop -t 120 slo_queue` (and prevent the 00:35 scheduler invocation), set the flag false, rebuild the Laravel configuration cache using the new image/environment, restart scheduler and SLO worker if pending jobs should be consumed as no-ops, and verify `config('monitoring.slo.automatic_preparation_enabled') === false` in **both** processes. Configuration cache files are per container/image, not shared by changing only the `app` container. Do not discard pending jobs or roll back SLO tables. For enable, obtain explicit operator approval, update the flag/cache, restart scheduler and dedicated worker together, and observe the first daily run. `queue:restart` alone is insufficient if a container immediately restarts with an old cached image/config. Already *executing* transactions cannot be retroactively canceled; stop/drain the SLO worker before changing the flag and inspect any proposal created during the boundary.

## Synthetic evidence and unresolved interference

Batch 5B's isolated MySQL 8.4.8 fixture held 500,000 checks. Exact percentile median for the largest selected service (18,219 raw / 16,856 valid latency observations) was 1,934.6 ms over five repetitions. A separate 50-job queue run dispatched 50 jobs in 2.434 seconds and drained them in 4.212 seconds; all 50 performed ranked calibration and created Draft proposals, **but each had only 28 checks**. The then-shared-queue 400-query indexed-read probe changed median/p95 from 0.845/3.173 ms to 1.069/3.470 ms during those light jobs. It did not measure real check dispatch or a dense SLO job.

Batch 5C.1 added **one bounded concurrent smoke** in a new no-volume MySQL 8.4.8 container (2 CPU/768 MiB), using the guarded 500,000-check fixture. One 18,219-history-check service was assigned a five-minute calibration cadence and sent to `slo-calibration`; ten one-minute HTTP services targeted only a local `/up` endpoint and were dispatched by the real `services:check-due` command to `default`. Both workers were forked at the same instant after dispatch; all ten check jobs **started and finished while** the 2,486-ms SLO job was executing. The SLO job created one Draft; all ten HTTP checks succeeded; both queues drained with zero failed jobs. A first attempted run whose worker periods did not overlap was **excluded** from this comparison.

These bounds derive from the application's one-minute minimum cadence, 20-second maximum request timeout, 30-second check-job timeout, and ten seconds reserved for persistence; they are **project operating criteria**, not Google/ISO thresholds. Also record SLO queue wait/runtime, worker RSS/CPU, MySQL p95 query and lock wait, and monitoring baseline-versus-concurrent distribution. Test one SLO worker, then at most two only if host/DB headroom permits; test stop/restart and pending-job disable. A short local test cannot establish production tail behavior or seasonal load. **The complete interference gate is not yet measured or passed; automatic activation is no-go.**

## Batch 5C.2 isolated operational acceptance — 16 November 2026

All observations below used **synthetic** data on a separate localhost-only MySQL **8.4.8** container capped at **2 CPUs / 768 MiB**, local PHP workers, and a localhost `/up` endpoint. No university endpoint, production database, credentials, or scheduler was accessed. The fixture held 500,000 deterministic historical checks across 50 HTTP/API services (1,399–18,219 each), plus ten separate one-minute localhost monitors per phase. The 50 historical services were kept eligible for calibration but given a daily *current* check cadence so their example URLs would not enter the operational queue. This is a load fixture, **not** a historical configuration-change validity study. The runner requires an exact disposable database name, user, port, server UUID, and guard token before fixture writes. Event-table instrumentation adds a small amount of database work.

The clean comparison ran one default-queue worker and, only in the concurrent phase, one SLO worker. It called real `services:check-due` twice at planned offsets 0 and 65 seconds and observed each phase for 90 seconds. The offset allows a first check to finish before its next one-minute opportunity, but is **not** an exact cron-minute simulation. The measured job-finish event fires after persistence, but is not a separately timestamped `service_checks` commit; the lateness column is relative to **planned** call offsets, not exact scheduler due minutes. Different synthetic service rows and non-randomized phase order limit causal comparison. Two exploratory attempts were rejected: one forced single-process nightly calculation blocked dispatch, and one accidentally put historical bulk services in the operational queue. Neither contributes to this clean table.

**Monitoring-opportunity ledger for these trials:** each phase planned two manual `services:check-due` calls across ten services, or **20 service-call pairs**; this is not an observed cron schedule or a verified *due-opportunity* denominator. The command's `isDue()` decision was not captured per service, nor was a continuous scan made through the 90-second cutoff. Planned-call start delay (`command_start - planned_offset`), queue wait (`Queue::before - payload_enqueue_time`), job execution (`Queue::after - Queue::before`), and this planned-to-job-finish lateness are distinct. The measurements are short, synthetic, non-randomized trials: the difference is neither a statistically significant effect estimate nor evidence of a production SLA violation.

**Project acceptance gate:** p95 planned-dispatch delay ≤5 s, p95 default-queue wait ≤10 s, p99 planned-due-to-result lateness ≤50 s, all *actually due* monitoring opportunities present, zero unexplained failed jobs, no default-worker heartbeat outage, controlled/drained SLO backlog, and no unacceptable database/host contention over a representative sustained duration. These are project operating limits based on the one-minute cadence and 20-second request / 30-second job timeouts, not Google or ISO rules. The measured delay percentiles were within bounds; the **19/20 planned** count cannot establish actual opportunity coverage, while **4/50** queue rows remained unfinished at the harness cap. Missing heartbeat/lock-wait/peak evidence, short duration, and synthetic service mix mean the **overall gate fails / remains unverified**. Automatic activation is **no-go**.

### Nightly overlap and worker recovery

The registered schedule remains `services:check-due` and Phase II `spc:evaluate` every minute; daily reliability **00:10**, SLA **00:20**, legacy charts **00:25**, and gated SLO eligibility **00:35** use the institution timezone (expected `Asia/Damascus`). Phase I preparation is researcher-triggered, not nightly. Laravel `schedule:work` starts a new `schedule:run` process each minute; within each process due events are sequential. A **forced single-process** overlap probe on the same fixture measured reliability **12.762 s**, SLA **0.013 s**, charts **81.860 s**, and Phase II **0.006 s**. Its second manual dispatch was **34.900 s** late and ten jobs remained when the capped worker stopped. This is a contention warning, **not** a faithful measurement of independent minute-level `schedule:work` processes; the measured chart command also ended well before the ten-minute gap to SLO preparation. The smallest operational response is to keep the SLO flag off and its queue isolated, then run a schedule:work-equivalent midnight overlap rehearsal with real minute boundaries and lock/CPU instrumentation before changing schedules or formulas.

With the SLO worker stopped, the scheduler enqueued **50** jobs on `slo-calibration`. In the concurrent trial, **46 jobs had completed and created Drafts** by the capped worker's return; **four job rows remained in the SLO queue**, with zero failed-job rows. The trial did not retain each remaining row's `reserved_at`/attempt history, so its output cannot distinguish ready, stale-reserved, or retrying states at that cutoff. None of the four is counted as completed or failed. In the subsequent recovery probe, a newly started worker was killed while handling one of these four: proposal count stayed **46**, one job was observed reserved, and no partial proposal appeared. Another pending job was consumed with the feature flag **off** in 53.45 ms; proposal count stayed **46**. After expiring only the killed synthetic reservation in the disposable database (simulating the 90-second lease), a restarted worker drained the other three: **49 unique Drafts**, no pending/failed jobs or approvals, and **49/49 strict digests verified**. Thus three of the original four were eventually prepared and one was intentionally skipped while disabled; their exact initial reservation states remain unrecorded. Two concurrent scheduler processes then saw one newly eligible service and dispatched just one job; it produced one additional Draft, and the final audit verified **50/50** digests. This tests isolated atomicity and duplicate suppression, not production crash recovery.

Config caching was tested with a separate temporary cache file: after caching the flag as **true**, an environment value of `false` still read **true**; after rebuilding the cache as **false**, an environment value of `true` read **false**. The temporary cache was cleared. Safe disabling requires stopping/draining the SLO worker, changing the flag, refreshing each container's cache, and restarting long-lived scheduler/workers. Editing `.env` alone is insufficient; an executing transaction cannot be canceled retroactively.

## Batch 5C.3 — frozen local acceptance criteria (set before its measurements)

These are **project-specific operational gates**, not Google or ISO latency standards. The default check worker polls the database queue (3-second idle sleep), each service becomes due 60 seconds after its preceding `checked_at` for a one-minute interval, and `services:check-due` is scheduled each minute. HTTP/API network execution is capped at 20 seconds; a check job at 30 seconds; the optional SLO worker has one 1-CPU/384-MiB container, a 256-MiB PHP limit, 55-second job timeout, and a separate `slo-calibration` queue. The disposable MySQL server will be limited to 2 CPUs and 768 MiB. **Do not silently supersede earlier criteria:** Batch 5C.1 proposed p95 ≤5 seconds from an actual due minute to dispatch and p99 ≤50 seconds from that due minute to result for future production acceptance; Batch 5C.2 measured its separate 5/50-second bounds against *planned manual calls*. Neither earlier proposal was formally approved or retired. The Batch 5C.3 limits below were frozen for this **local adaptive-due workload** before measurement; they do not resolve the stricter proposed production gate. Minute polling can itself add almost 60 seconds after an actual due timestamp.

For a bounded local test, freeze these limits **before** comparing outcomes: (1) every eligible opportunity due before the observation cutoff must have a successful persisted result by a 105-second completion grace; report the full state ledger at cutoff and grace, with no double-counting; (2) p95 actual-due-to-dispatch ≤65 seconds (60-second poll plus 5-second command margin), p95 dispatch-to-start ≤10 seconds, and p99 actual-due-to-`Queue::after` ≤105 seconds (poll margin + queue margin + 30-second job allowance); (3) no unexplained failed check/job, normal-queue backlog zero by grace and no missing monitoring-worker heartbeat; (4) a single dedicated SLO worker must drain its bounded cohort within 300 seconds of dispatch, with no failed job, duplicate or partial frozen proposal, and a disabled pending job must remain inert; (5) no OOM, host available memory ≥1.5 GiB and free disk ≥8 GiB, SLO PHP peak <256 MiB, MySQL below its 768-MiB cap, no observed lock wait >1 second, and record baseline/concurrent SQL and host/container CPU/RAM rather than asserting equal-load causality. Exceeding a limit is **FAIL**; an absent denominator, missing instrumentation, unrepresentative workload, or insufficient repetitions is **UNVERIFIED**, not PASS. Passing local gates does not certify production capacity.

The due timestamp is the preceding persisted `checked_at + check_interval_minutes`; for a new service with no check, the harness uses its recorded phase start as an explicit **activation-time proxy** (the application does not persist a separate activation timestamp). A due event is counted once until a check starts, not again at every scheduler poll. The observation cutoff and 105-second grace are fixed before the run. Use `hrtime()` for elapsed process timing and UTC timestamps for cross-process/event correlation; do not confuse `Queue::after` with a separately timed database commit. A service-call plan is **not** itself the due-opportunity denominator. When no worker or fixture can provide a faithful local schedule/lock trace, retain the corresponding gate as UNVERIFIED.

### Disposable workload and opportunity ledger

The bounded runner is `tests/Benchmarks/slo_operational_acceptance.php`. It refuses any database except a named loopback-only MySQL 8.4 disposable schema with a matching server UUID and one-time guard token, checks free disk, and never targets university URLs. A fresh MySQL **8.4.8** container (2 CPUs, 768 MiB) held the deterministic Batch 5B 500,000-check, 28-complete-local-day fixture: 50 high-volume HTTP/API services with **1,399–18,219** historical checks each, including deterministic failures, missing latency, manual and maintenance exclusions. Each also received one *manual* post-cutoff marker solely to prevent its `.invalid` fixture URL from entering the operational monitoring queue; the marker cannot enter the frozen calibration window. The baseline and concurrent phases each used a different set of 20 otherwise identical local HTTP/API monitors pointing to `127.0.0.1:18081/up`, with no external request. The same five planned `services:check-due` calls were made at monotonic offsets 0, 60, 120, 180 and 240 seconds. The cutoff was 300 seconds from phase start, followed by 105 seconds of completion grace. Both phases used one normal database-queue worker; the concurrent phase also used one dedicated `slo-calibration` worker and an explicit `slo:prepare-due` dispatch of **50** heavy jobs. That job cohort was processed sequentially by one worker, not by 50 simultaneous CPU workers. The pre-existing one-service 18,219-check calibration result (2.486 seconds) served as the earlier lower-load step; this batch did not invent an unmeasured intermediate cohort.

The runner records a **payload-construction timestamp** in Laravel's `Queue::createPayloadUsing` hook, then `Queue::before`, `Queue::after`, persisted check outcome, queue state at cutoff, and failed jobs. The output's `dispatch_wall`/`due_to_dispatch_s` names refer to that **pre-enqueue** marker, not a separately timestamped successful database insert. Each command reported zero failed dispatches and ran at most **0.518 seconds** (baseline) or **0.434 seconds** (concurrent), so its successful enqueue occurred by command return; even adding each phase's maximum command duration to its maximum marked due→dispatch delay yields conservative due→enqueue bounds of **58.249** and **59.195 seconds**, below the new 65-second local criterion. This bound does not assert exact enqueue latency. The runner computes marker→start and start→`Queue::after` elapsed time with `hrtime()`; UTC wall times link the process events to each prior persisted `checked_at + 60 seconds`. `checked_at` is the checker-start time stored at database-second precision; `Queue::after` occurs after persistence and post-job handling, not at a separately timestamped commit. The first opportunity uses the recorded phase activation. Percentiles below use R Type 7 interpolation over the **60 completed due opportunities** in each phase. The cutoff state partitions every due opportunity exactly once into completed success, completed failure, running, dispatched/pending, or due/not-dispatched; the same cohort is checked again at grace. A future opportunity is counted as *not yet due*, never as failed. These are monitoring-opportunity metrics, not the response-time SLI or browser latency.

## Migration and frozen-data review

The ordered migrations are `2026_11_16_000001_create_slo_proposals.php` followed by `2026_11_16_000002_allow_system_created_slo_proposals.php`. The first creates a new table only: service foreign key with `RESTRICT` deletion, unique immutable identity digest, `(monitored_service_id,status)` index, JSON payload and actor/lifecycle fields. The second makes `created_by` nullable so system-created drafts have `NULL` while human attribution remains recorded. Neither changes `service_checks`, SPC tables, or historical classifications. `down()` for the table refuses to discard any proposal; the nullable-field rollback refuses to lose system provenance. Do **not** use migration rollback as ordinary recovery. A disposable MySQL **8.4.8** upgrade simulation applied all earlier migrations, inserted a synthetic pre-existing service/check (latency 123 ms), then applied these two migrations in order. The service and check survived with the same count/value; `created_by` was nullable, the unique/index/FK metadata matched, and `slo:audit-frozen` reported zero proposals. This is compatibility evidence for a small representative schema, not a production-size lock-time measurement. Before production change, review the actual migration ledger and table presence; a partially deployed schema needs investigation, not blind reruns.

`php artisan slo:audit-frozen` is a **read-only** diagnostic. It reports table absence and separate counts for verified, digest/field-mismatched, and unverifiable records; at most 50 IDs per problem class are printed. A table-read failure marks the audit incomplete, never successful. It calls the same strict frozen-payload/identity checks as lifecycle actions and never edits data or calls calibration. On an existing installation, run it only through an authorized read-only database connection or supervised application CLI, first confirming the table and row count. Zero proposals is not evidence of a historic incident. Any mismatch—whether genuinely altered data or an older MySQL JSON representation difference—requires a separate forensic review with trusted original evidence; an unverifiable record also needs investigation. Do not normalize, rewrite, or automatically excuse a digest. Record output and DB snapshot ID. Existing approved proposals remain immutable and are not affected by the auto-preparation flag.

## Permissions, backup, and recovery prerequisites

`RolesAndPermissionsSeeder` currently assigns `slo.proposals.manage` to administrator and super_admin, **not** operator/viewer; `reliability.view` and `control_charts.view` are available to ordinary authorized readers. Thus every existing administrator may already be an SLO approver if that seeder ran. Do not run a production seeder blindly: it uses `syncPermissions` and can replace customized role grants. Inventory actual roles/grants **and individual administrator accounts**, obtain owner approval for any change, create only missing permission records through the reviewed deployment mechanism, and retain SLO management only for specifically authorized research approvers. Test read-only viewers and forbidden review/approval on the deployed image. Preserve human review notes, limitation acknowledgement, and audit logs. The SLO worker requires database queue/cache access and proposal insert, but no web user role; normal web authorization remains server-side.

Before deployment, operator records current commit/image digests, schema migration ledger, UTC clocks, settings, service/queue counts, and available space. In a change window with no schema DDL concurrent with backup, use the existing pre-update checkpoint and record its private bundle path:

```bash
docker compose exec -T app php artisan backup:create --pre-update
docker compose exec -T app php artisan backup:verify /var/backups/svu-quality-monitor/REVIEWED_BUNDLE
```

Inspect the result, checksum manifest, size, migration list, and off-host custody. The commands, privilege rules and restore limitations are in `docs/backup-and-restore.md`; never place credentials on a command line or copy production dumps into this repository. In a **separately named isolated Compose project with disposable DB/storage and the compatible image**, transfer a protected copy of the reviewed bundle, keep its scheduler/queue stopped, and invoke `php artisan backup:restore /var/backups/svu-quality-monitor/REVIEWED_BUNDLE --force --workers-stopped --actor-email=EXISTING_SUPER_ADMIN_EMAIL` **only inside that isolated project**. Verify restored row counts, key research digests, file manifest and application login, then destroy only the disposable drill environment. Have a second operator verify the project name, target database and volume names before the restore command. The repository's `scripts/verify-backup-isolated.sh` tests restore machinery with *synthetic* data but does not by itself validate a copy of the actual pre-deployment bundle. A checksum-only verification is not a restore test. These are future operator procedures and were **not executed against production** in this batch.

Rollback preference: set the auto flag false and stop the SLO worker, preserve all Draft/Reviewed/Approved/Retired proposals and job/audit evidence, then revert application images only after checking the older image tolerates the additive schema and queued payloads. Do not run `migrate:rollback`, `migrate:fresh`, `docker compose down -v`, delete proposals, or restore an old dump over newer research records as a routine response. If the old image is incompatible, keep the feature off and forward-fix from an isolated restore; a full database restore needs a separately authorized data-reconciliation plan.
