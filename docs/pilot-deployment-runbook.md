# Pilot deployment and rollback — R5

This is a runbook for a later authorized deployment. R5 development does not deploy research migrations to the operating database, create real services, start Pilot, commit or push.

## Before the maintenance window

1. Use the approved policies in `research-pilot-protocol.md`: seven complete days, 4–6 authorized HTTP/API services representing different functions, five-minute monitoring, automatic-only direct research samples, UTC storage/Asia/Damascus analysis, I/MR/P with hourly P, 30-minute episode gap and 60-minute association horizon. The 95% coverage target is an operational Pilot acceptance policy, NOT a universal statistical/SPC rule. Record the remaining exact service IDs/permissions/settings, UTC dates, preliminary-reference decision and custody/operational details; do not reopen resolved policy choices. Pilot validates measurement/data quality, not final thesis inference. Pilot end must not create or approve a baseline automatically.
2. Review `git status` and exact R1–R5 changes. Through the normal authorized workflow create/review the release commit later, record its hash, build immutable app/web images and record image digests. A current dirty HEAD is not the frozen research release.
3. Verify fresh/upgrade tests against MySQL 8.4 and the current image, not a bind-mounted checkout. R5's isolated compose is `docker/compose.research-test.yml`; it has its own project-scoped database/storage, test-only credentials, loopback port and internal network. Never substitute the production project name or volumes.
4. Inventory the current migration ledger, application/schema versions and installed role customizations. Keep the four research migration names in their existing order. Filename dates sort migrations; they do not delay execution until a calendar date. Do not rename a migration on the assumption that no other persistent environment ran it.
5. Create and verify a backup using the existing backup tooling, including database and relevant storage/configuration custody. Test restoration into a separate database and verify checksums/counts. Record the backup ID/location and old image digests. A file existing is not a verified backup.

## Controlled deployment

1. Pause collection/queue/scheduler during the change window so pre-change and post-change data are distinguishable and no old worker runs new-schema jobs. Record the UTC gap; do not classify it as healthy.
2. Stage the reviewed code/images (`git pull` only if that is the deployment mechanism). Build before activation. `docker-compose.yml` packages source into images and shares application storage; do not mount host source as a substitute for the build.
3. With the **new application image** and correct production environment, inspect `php artisan migrate:status`. Apply the pending forward migrations using `php artisan migrate --force` only after backup verification and deployment authorization. Do not use `migrate:fresh`.
4. Run the required permission seeder explicitly: `php artisan db:seed --class=RolesAndPermissionsSeeder --force`. Production DatabaseSeeder is factory-free and creates no demo user; the explicit permission command makes intent clear. Built-in role permission lists are authoritative, so review custom grants before reseeding. Provision real administrator accounts through the approved account workflow.
5. Run `php artisan optimize:clear` in the new app context, recreate app/web/queue/scheduler from the matching image versions, and ensure permissions on shared storage/cache. Old long-running workers must not survive the release switch.
6. Inspect `schedule:list`, scheduler heartbeat, queue heartbeat, failed jobs and logs. Verify the database session clock is UTC or equivalent; compare UTC application/PHP/system/database times and Asia/Damascus analysis time. Keep database storage UTC.
7. Smoke-test login, dashboard, services, Reliability, exploratory charts, Baselines, Phase II, reports and research export. Synthetic out-of-control/incident scenarios must run in the isolated environment only. Production smoke must not deliberately fail real endpoints.
8. Save `research:configuration` output, release commit/image digest, signed protocol and UTC deployment timestamp in the research archive. Review source digest/dirty status. Record the custodian/archive and verified-backup cadence. Verify that raw research data will be preserved throughout the study and no automatic cleanup deletes Pilot raw observations; the policy is approved, while this runbook does not change settings.
9. Only after explicit researcher start approval, enable the selected 4–6 approved services at five-minute intervals and record the actual Pilot start and end in UTC, spanning seven complete days. Verify first automatic checks, exclusions/coverage and queue-delay context. Phase II may legitimately remain `no_approved_baseline` if no preliminary reference has been approved; do not silently generate one.
10. Monitor natural events and diagnostic queue delay/coverage against the approved 95% operational target using existing coverage semantics. Record and exclude planned maintenance under existing research policy. Manual checks remain operational and excluded from the direct research sample; necessary manual intervention must record its UTC timestamp, reason and action, with review of the affected segment. Preserve periodic `research:export --from=<UTC> --to=<UTC> --output=<new-directory>` packages and manifests. Do not change thresholds/horizon on outcomes. Log major configuration changes and treat them as measurement-phase boundaries. Preserve raw observations throughout the study; no automatic Pilot raw-data deletion. At Pilot completion, review data quality without automatically creating or approving a Phase I Baseline.

## Rollback: protect data first

1. Pause affected collection/workers, record UTC time/reason and capture logs, current snapshot and failed-job evidence. Take an additional verified backup if new research data exist.
2. Prefer reverting the application image/code to the recorded previous release **only after checking that it tolerates the forward schema**. In particular R2 nullable availability and R3's removed old uniqueness constraint mean strict old assumptions need review. Do not blindly run the old calculator against changed semantics.
3. Keep new research tables and archive evidence. A code rollback does not require deleting new columns/tables. If safe old-code compatibility cannot be established, keep collection paused and forward-fix in an isolated restored database.
4. Migration `down()` is a schema test, not a production recovery plan. R4A/R4B rollback drops research evidence; R2/R3 drop research context. R2 intentionally does not restore NOT NULL availability; R3 intentionally does not recreate a uniqueness constraint that cannot represent valid coexisting analyses. Never delete rows to make rollback pass.
5. If full restoration is necessary, restore the verified backup into a separate database, assess data collected since backup and reconcile/archive it, then switch only under an approved recovery procedure.
6. Verify health, schema/image match and exports before resuming. Mark the interruption and new segment explicitly.

Forbidden recovery shortcuts: `migrate:fresh`, `docker compose down -v`, deleting the DB volume, or overwriting the only backup. No rollback is executed on production by R5.
