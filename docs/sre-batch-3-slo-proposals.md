# Batch 3: immutable SLO research proposals and independent evaluation

This batch persists Batch 2's provisional, data-derived calibration without creating an operational service-level objective. The frozen payload contains the complete 28-local-day UTC calibration interval and cutoff, policy version, Type 7 P90/P99, exact rounded latency objective, 99% research-policy target, S/N, G/V and G/N denominators, coverage and missing opportunities, configuration fingerprint, warnings, and proposal fingerprint. `payload_digest` is SHA-256 of canonical JSON, and `identity_digest` uniquely identifies service, policy, period, cutoff, and configuration. The application checks both before lifecycle changes or evaluation. Identical preparation returns the existing record, including when approved; the service row lock and database unique constraint serialize concurrent preparation. An altered historical check never silently updates an existing proposal.

The additive `slo_proposals` migration has a restrictive service foreign key, unique identity digest, and no writes to existing research or monitoring tables. Its rollback refuses to drop a table containing retained proposals; an empty new table may be removed. Reviewer and approver IDs are retained as historical actor IDs even if accounts are later removed. The approved objective stays provisional research calibration, not a validated user-experience target, an official Google numerical standard, or an activated warning/critical configuration. Approval does not mutate monitoring settings or start evaluation. Only active users with `slo.proposals.manage` (administrator or super administrator by seeded roles) can create, review, approve, or retire; review requires notes and explicit limitations acknowledgement, approval requires rationale and adequate calibration data, and retirement requires a reason. The seeder grants the new permission to those existing roles only when run through a separately authorized deployment process; Batch 3 does not run it on production. Configuration mismatch prevents approval; after approval, evaluation reports a mismatch instead of recalibrating.

`SloEvaluationAnalysis::evaluate()` is an explicit, read-only call, not a scheduler or UI action. Calibration is `[calibration_start, calibration_end)` and evaluation is `[evaluation_start, evaluation_end)` in UTC. Since `calibration_end = calibration_cutoff` is exclusive, an evaluation beginning **exactly at the cutoff** is valid and non-overlapping; a start before it is rejected. Evaluation is bounded to 29 elapsed days to constrain coverage memory and permit 28 local days across a daylight-saving transition. Only an approved proposal can be evaluated. The caller must choose and record a post-cutoff interval; Batch 3 does not introduce a researcher-facing selector. It uses the existing eligible automatic HTTP/API cohort, maintenance exclusions, and no-lookahead record cutoff. In one transaction snapshot it reports availability `S/N`, conditional successful latency `G/V`, combined success-and-latency `G/N`, all counts, current-cadence expected/covered/missing opportunities, and frozen-threshold margin versus the provisional combined target. `N=0` gives null availability and combined SLI; `V=0` gives null conditional SLI. Failed checks or successful checks with absent/invalid latency are never good combined events. Missing opportunities are coverage uncertainty, never healthy checks. A shortfall is called only when there are executed checks, at least 95% current-cadence coverage, and compatible current configuration; otherwise the result is `insufficient_evidence` with warnings. The 95% threshold and 99% target are versioned research-policy choices, not Google or ISO mandates. Calibration warnings, including unattainability when calibration availability is below 99%, remain visible.

Evaluation mode is based on the frozen approval timestamp, not on when a later report is requested. A window ending at or before approval is `post_calibration_retrospective`; any assessable result is named `retrospective_met` or `retrospective_shortfall`, **not** prospective approved-SLO compliance. A prospective window must start strictly after approval and is `prospective_after_approval`, with `met` or `shortfall` when assessable. A window crossing approval, including one starting exactly at the approval instant, is rejected and must be split. Retrospective evaluation remains useful as independent post-calibration research, but does not establish prospective operational compliance.

The current configuration fingerprint cannot reconstruct every historical configuration or maintenance edit. Current-cadence coverage estimates are not proof that every scheduled check was attempted, and small-sample P99 is an exploratory tail estimate with unquantified uncertainty. A period with matching current configuration might still contain intermediate changes. Evaluation is independent in time but is not proof of externally validated user experience, nor is it an operational SLO before a separate governance decision. This batch does not change `response_time_ms` (synthetic check duration), SPC formulas, Phase I/II records, incident history, or historical classifications.
